# Native control executor and helper

The new `AstraControl` Swift executable owns desktop input independently of the application UI. `InputExecutor` schedules validated timed packets against the host monotonic clock, with a 500 ms renewable ownership lease, a separate watchdog, a bounded queue (32 packets / 8,192 scheduled entries), and a per-user exclusive desktop lock shared across Astra libraries. Lock descriptors are close-on-exec and final symbolic links are rejected.

`CGEventControlBackend` constructs actual Core Graphics key, modifier, button, pointer and pixel-scroll events. Its private event source and synthetic-event tag distinguish owned input from physical state. Apple documents separate private and HID state tables in [CGEventSourceStateID](https://developer.apple.com/documentation/coregraphics/cgeventsourcestateid). No real event posting has been exercised in this verification.

## Scheduling and cleanup

- Admission checks the complete packet's run, sequence, geometry, capabilities, timing, capacity and supported arguments before changing the queue. Relative deltas require integral raw counts. Absolute action coordinates use `[0,1)`; the generic image-boundary geometry APIs remain separate.
- Absolute trajectories interpolate within the same surface at one millisecond steps. Relative interpolation uses cumulative rounding to nearest-even and a final remainder, preserving the exact commanded raw-count total. Interpolated motion precedes explicit edges at the same timestamp, matching the practice scheduler.
- Relative motion, clicks, scrolling and cleanup use the current native cursor location, so an application's cursor warp does not accumulate deltas against an obsolete synthetic position or move the cursor back during button release. This behavior has virtual-backend coverage; target-observed pointer-lock behavior remains a live qualification.
- Key/button holds are idempotent. The executor reserves possibly posted holds before leaving its lock to call the backend. The watchdog can invalidate the run while posting is blocked; a returning stale post repeats owned cleanup. The in-flight packet's terminal receipt waits for that return, retaining its actual result instead of claiming that posting never happened.
- Watchdog and event-tap stops invalidate admission synchronously and dispatch release work to the independent stop queue. A blocked release cannot hold the watchdog. Signal and sleep callbacks invalidate arming without waiting for the server actor, and physical takeover/emergency events during monitor startup latch until the arming handshake finishes.
- Cleanup releases only owned controls and does not release controls currently held physically. An overlapping physical hold takes ownership. Failed release attempts remain in the ledger and keep the desktop lock until retry succeeds; a new run cannot arm during posting or cleanup.
- A configurable 20 ms maximum lateness is checked before and after scope verification and after posting. Receipts distinguish admission, execution, rejection, cancellation and lateness, with each original command's scheduled time and posting API return time. They establish API posting evidence, not target consumption. Individual interpolated samples are not separately emitted as command receipts.
- The helper's passive input monitor provides emergency stop and physical takeover independently of UI responsiveness. EOF, malformed transport, output backpressure, shutdown and sleep request disarm. Graceful disarm/shutdown acknowledge only settled cleanup. If posting remains in flight or release fails, the helper remains alive and retains desktop ownership after its parent disconnects. Forced helper termination and actual OS cleanup under revoked posting access remain release qualifications.

## Permissions and scope cost

Arming requires existing Accessibility, Input Monitoring and event-posting permissions. No permission prompt or grant is issued by the helper. Caps Lock, Fn, media and power-key capabilities are explicitly rejected pending qualification.

Read-only profiling on the available M3 Max identified a serious hot-path mistake: repeated permission preflight calls cost approximately 9–10 ms each. The full window-list query itself measured approximately 0.35–0.39 ms. Moving permission checks to an independent 100 ms poll, with a conservative 250 ms freshness limit measured from the start of the check, reduced the measured whole-desktop scope check from 18–21 ms to approximately 0.025 ms. This probe created no executor lease, event tap, or posted input.

The independent scope poll runs every 20 ms and expires evidence after 100 ms. Scope failures latch until an explicit new arm; generation checks prevent an old poll from affecting a new target. The watchdog reads cached health only, so a blocked WindowServer or permission query cannot block lease invalidation. Every command still performs fresh target verification before posting. Whole-desktop and display-pointer scopes use display identity/geometry directly; application/window scopes check foreground identity, launch identity, geometry and conservative pointer hit ownership. Fresh window checks still need end-to-end cadence and latency qualification; no cached approximation has replaced them.

## Evidence and limits

On 2026-09-11, 22 executor/desktop-lock tests passed using an injected clock and virtual posting backend. They cover taps/repeats/idempotence, atomic packet rejection including the normalized endpoint, exact motion interpolation and receipts, application cursor warps, expiry, independent automatic watchdog scheduling, blocked posts and cleanup, stale arming, scope checks racing stop, post failures after possible effects, late posts, unknown physical state, queue/history bounds, cursor acknowledgement, physical takeover, permission-health failure, failed-release retry, exclusive desktop ownership and side-specific modifier bits. The final `swift test` run passed 101 tests in two suites (4.939 seconds), including the concurrently integrated inference and learning coordinator checks.

`scripts/check_control.py .build/debug/AstraControl` exercises the actual compiled helper with a minimal PATH-only environment: ordered request/reply correlation, unarmed state/disarm/shutdown, inactive observation/heartbeat rejection, empty EOF, malformed/truncated/oversized input, invalid sequence, SIGTERM while stdin remains open, and 50,000 requests with stdout deliberately unread. No arming, permission request, or posting occurs. This campaign exposed and fixed a SIGTERM crash caused by a dispatch callback inheriting main-actor isolation; signal/sleep callbacks now declare their sendable execution explicitly.

The wire advertises implemented `ping`, `permissions`, `arm`, `heartbeat`, `execute`, `disarm`, `observation`, `state` and `shutdown` operations. Asynchronous `control.receipt` messages retain packet/run/request identity. `control.stopped` retains run identity and has a stable `cause` (`physicalTakeover`, `emergencyStop`, `requested`, `shutdown`, `disconnected`, `sleep`, or `fault`) plus readable `reason`. Stdout must successfully enter nonblocking mode and is bounded to 4 MiB; a stalled consumer triggers independent disarm. Stdin uses bounded POSIX reads and the versioned framer.

`observation` requires the active run and accepts an optional `afterSequence` acknowledgement. Its direct acknowledgement payload contains `controlState`, `executedEvents`, `intervalCovered`, `cutoffNanos`, and optional `lastSequence`. The state and executed-event history are captured under one lock at one cutoff. Posting/cleanup in flight makes state invalid, silence preserves the last state-observation time, and no-op holds produce no fabricated posted event. Clients may acknowledge only history already delivered in that run. At most 2,048 unacknowledged events are retained; overflow invalidates coverage and stops execution rather than silently discarding history.

This is not installed-app or physical-control qualification. Bundled-helper TCC attribution, actual key/button/scroll effects, input revocation, application/window cadence, overlays and programmatic focus changes, helper termination, sleep/wake, actor/UI connection, target-observed receipts and release from the final DMG remain open product gates. macOS does not permit successful synthetic cleanup when posting access itself is revoked; pending owned state must remain visible through the UI/client integration.
