# Secure Event Input and keyboard trust

The installed macOS Carbon SDK declares `IsSecureEventInputEnabled` **not thread safe**. Its companion API documentation describes Secure Event Input as suppressing keyboard monitoring outside the focused application. The relevant primary source is `HIToolbox.framework/Headers/CarbonEventsCore.h` in the Xcode macOS SDK, in the Secure Event Input section. This does not document a universal return value for every `CGEventSource.keyState(.hidSystemState)` query while Secure Input is active. Astra consequently treats complete keyboard observation and physical-hold attribution as unavailable, rather than assuming that an empty HID query proves that no person holds a key.

`KeyboardObservationTrust.shared` is the sole production probe in each process. All Carbon calls execute on the main thread. It samples every 20 ms and rejects cached proof once 150 ms old, measured from the beginning of the query. Scheduler, event-drain, and watchdog reads use only a short cache lock; they never synchronously dispatch to the main thread or call Carbon. Cold arming and cleanup explicitly obtain fresh main-thread proof. The guardian's synchronous recovery loop already runs on its own main thread, so those cleanup probes do not depend on its timer being serviced.

An interruption generation records every observed transition from trustworthy to active Secure Input or stale verification. Clearing Secure Input does not restore an existing recording or armed run: an explicit new start is required. Recording continuity emits one terminal boundary from that recording's last trusted sample, including when Secure Input was observed and then cleared between event deliveries. The recording writer retains raw evidence but excludes the uncertain interval using its existing `firstInvalidObservedNanos` contract.

Control arming and monitor startup reject active Secure Input before admitting control or creating an event tap. Physical-state reads become invalid while proof is unavailable. Cleanup checks fresh trust around its HID snapshot and immediately around the final physical-hold recheck for an owned release. Untrusted snapshots or rejected releases leave possible holds and the desktop lease pending; the surviving executor or guardian retries when trustworthy observation returns. An unarmed helper still supports its ordinary offline protocol operations. No new privacy permission is requested, and Astra never enables or disables Secure Event Input.

## Verification

The permission-free `SecureInputTests.swift` fixtures cover main-thread probe serialization, cached reads with no probe calls, initially unknown and stale proof, rejection despite all privacy grants, interrupted HID sampling, native cleanup rejection before posting, monitor rejection before tap creation, recording exclusion from the last trusted sample, and retained owned cleanup/desktop lease followed by recovery after injected trust returns. Native posting remains the production implementation; the owned-release recovery fixture records virtual emissions only.

On 2026-09-12, all eight new Secure Input tests passed. The combined platform, recording/recovery, and inference run passed 90 Swift tests; a final focused run passed 19. Both builds were warning-free. `scripts/check_control.py .build/debug/AstraControl` passed all eight ordinary helper protocol checks without arming or requesting permissions. Logs are kept locally at `.local/secure-input-integration-fixed.log`, `.local/secure-input-final-focused.log`, and `.local/secure-input-control-protocol.log`.

The integration run also exposed an intermittent pre-readiness guardian exit-watch race, now fixed and independently fault-tested; see [guardian verification](control-guardian.md). This was a failed run that prompted a correction, not a test disabled to obtain a passing result.

## Limits

Polling is bounded detection, not an atomic macOS transaction. A secure interval that begins and ends entirely between probes can remain unobserved, and no public API used here atomically combines Secure Input state, HID state, and event posting. The 150 ms freshness bound also limits reliance on a stalled main thread. The fixtures establish Astra's state transitions and conservative ownership behavior, not the exact behavior of every physical HID device or target under actual Secure Input. Installed-app privacy attribution, real input effects, and secure-input behavior in live target applications remain separate qualifications.
